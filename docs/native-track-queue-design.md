# Native Track Queue Design

## Status and scope

This document fixes the cross-platform contract for the opt-in persistent track queue developed on `feature/native-track-queue`. The queue is generic plugin functionality; it contains no SGDMS schema, credentials, endpoints, or `GISElements` logic.

Existing `start()` consumers remain unchanged. Native persistence is enabled only when `persistentTrack` is present in `StartOptions`.

The queue owns a private SQLite database inside the host application's sandbox. It never opens the host application's primary database.

## Invariants

1. At most one persistent track session is active at a time.
2. A location accepted for a persistent session is committed to SQLite before it is emitted to JavaScript or submitted to the optional native URL.
3. Points are assigned a strictly increasing sequence inside their session and are returned in that order.
4. Reads do not remove points. Only an explicit acknowledgement or reset removes them.
5. Repeating a read or acknowledgement is safe.
6. A crash after reading and before acknowledging leaves the points available for another read.
7. `stop()` resolves only after all location callbacks accepted before the stop boundary have committed or failed explicitly.
8. Queue overflow and storage errors fail closed: the session is marked accordingly and native tracking is stopped instead of silently producing an incomplete track.
9. The existing callback-only and native-URL-only modes preserve their current behaviour when `persistentTrack` is absent.

## Public API

The authoritative declarations and generated API documentation will live in `src/definitions.ts`.

### Start option

```ts
export interface PersistentTrackOptions {
  sessionId: string;
  maxPoints?: number;
}

export interface StartOptions {
  // Existing options remain unchanged.
  persistentTrack?: PersistentTrackOptions;
}
```

`sessionId` is an opaque identifier generated by the host application. It must be non-empty, no longer than 128 characters, and contain only ASCII letters, digits, `.`, `_`, `:`, or `-`. A UUID is recommended.

`maxPoints` defaults to `100000`, with an accepted range of `2` through `1000000`. The configurable limit permits fast overflow tests while keeping a generous production default.

Starting with a new ID creates an active session. Starting again with the same ID while that session remains active reattaches the new plugin/WebView callback and resumes native updates without creating another session. Starting another ID while a session is active fails with `ACTIVE_SESSION_EXISTS`. A stopped, overflowed, or failed session cannot be reopened; use a new ID or explicitly reset it.

### Session model

```ts
export type PersistentTrackSessionState = 'active' | 'stopped' | 'overflowed' | 'failed';

export interface PersistentTrackSession {
  sessionId: string;
  state: PersistentTrackSessionState;
  startedAt: number;
  stoppedAt: number | null;
  lastSequence: number;
  acknowledgedThrough: number;
  queuedPointCount: number;
  maxPoints: number;
  lastPersistedAt: number | null;
  droppedPointCount: number;
  errorCode: string | null;
  errorMessage: string | null;
}
```

`active` means that the session has not crossed an explicit stop/failure boundary. It is recoverable intent, not a promise that the operating system is currently executing the process. After an Android force-stop or an iOS force-quit, the application must query the session and call `start()` again with the same ID when platform rules permit.

### Point model

```ts
export interface PersistentTrackPoint extends Location {
  sessionId: string;
  sequence: number;
  persistedAt: number;
}
```

`time` remains the provider timestamp from `Location`. `persistedAt` is the native wall-clock time immediately before the successful SQLite insert. Sequence, not provider time, defines stable queue order because providers may deliver delayed or out-of-order timestamps.

Methods added to `BackgroundGeolocationPlugin`:

```ts
getActivePersistentTrackSession(): Promise<PersistentTrackSessionResult>;
getPersistentTrackSession(options: GetPersistentTrackSessionOptions): Promise<PersistentTrackSessionResult>;
getPersistentTrackSessions(): Promise<PersistentTrackSessionsResult>;
getPersistentTrackPoints(options: GetPersistentTrackPointsOptions): Promise<PersistentTrackPointsResult>;
acknowledgePersistentTrackPoints(
  options: AcknowledgePersistentTrackPointsOptions,
): Promise<AcknowledgePersistentTrackPointsResult>;
resetPersistentTrackSession(
  options: ResetPersistentTrackSessionOptions,
): Promise<ResetPersistentTrackSessionResult>;
```

Query rules:

- `afterSequence` defaults to the session's `acknowledgedThrough` value and must be a non-negative integer;
- `limit` defaults to `1000`, with an accepted range of `1` through `5000`;
- `points` contains queued rows with `sequence > afterSequence`, ordered ascending;
- `nextAfterSequence` is the last returned sequence, or `null` when no point is returned;
- `hasMore` is computed inside the same read transaction;
- session lists are ordered by `startedAt` descending so a stopped-but-not-imported session can be recovered after an application crash.

Acknowledgement rules:

- `throughSequence` is inclusive and must not exceed `lastSequence`;
- acknowledgement deletes queued rows with `sequence <= throughSequence` in one transaction;
- `acknowledgedThrough` only moves forward;
- acknowledging the same boundary again succeeds with `deletedPointCount: 0`;
- native HTTP success never acknowledges this queue because native delivery and host-application import are independent consumers.

Reset rules:

- reset is the explicit destructive operation for one named session;
- if the named session is active, reset first crosses the same stop boundary as `stop()`, removes the foreground service/indicator, and waits for accepted writes;
- it then deletes the session and all its remaining points in one transaction;
- an unknown session ID returns `deletedPointCount: 0`, making retry safe;
- there is deliberately no unscoped `resetAll` operation.

## `stop()` behaviour

The existing `stop(): Promise<void>` signature remains unchanged.

For a persistent session, native stop performs this ordered sequence:

1. prevent new provider callbacks from entering the accepted set;
2. unregister native location updates;
3. wait for every already accepted queue write;
4. mark the session `stopped` and set `stoppedAt` in SQLite;
5. clear persisted restart configuration;
6. remove the Android foreground service or iOS background indicator;
7. release the JavaScript callback and resolve the stop call.

Calling stop when no watcher is attached remains idempotent. If an active persisted session exists after plugin recreation, stop still finalizes that session.

## SQLite schema

Both platforms implement the same logical schema using the system SQLite library. Schema evolution uses SQLite `user_version`; schema version is not duplicated in every session row.

```sql
CREATE TABLE persistent_track_sessions (
  session_id TEXT PRIMARY KEY NOT NULL,
  state TEXT NOT NULL,
  started_at INTEGER NOT NULL,
  stopped_at INTEGER,
  last_sequence INTEGER NOT NULL DEFAULT 0,
  acknowledged_through INTEGER NOT NULL DEFAULT 0,
  max_points INTEGER NOT NULL,
  last_persisted_at INTEGER,
  dropped_point_count INTEGER NOT NULL DEFAULT 0,
  error_code TEXT,
  error_message TEXT
);

CREATE UNIQUE INDEX one_active_persistent_track
ON persistent_track_sessions(state)
WHERE state = 'active';

CREATE TABLE persistent_track_points (
  session_id TEXT NOT NULL,
  sequence INTEGER NOT NULL,
  latitude REAL NOT NULL,
  longitude REAL NOT NULL,
  accuracy REAL,
  altitude REAL,
  altitude_accuracy REAL,
  simulated INTEGER NOT NULL,
  speed REAL,
  bearing REAL,
  provider_time INTEGER,
  persisted_at INTEGER NOT NULL,
  PRIMARY KEY (session_id, sequence),
  FOREIGN KEY (session_id) REFERENCES persistent_track_sessions(session_id) ON DELETE CASCADE
);
```

Each point insert and the corresponding `last_sequence` / `last_persisted_at` update occur in one transaction. Queue counts are queried from `persistent_track_points` rather than maintained as a second mutable counter.

The database file is private to the plugin inside the host application's sandbox. Foreign keys are enabled. Android uses `SQLiteOpenHelper`; iOS uses the system `SQLite3` library. Neither platform adds a third-party database dependency.

## Queue limit and storage failure

When the number of unacknowledged points reaches `maxPoints`, the next accepted provider location is not inserted. In one transaction the native implementation:

1. changes the session to `overflowed`;
2. sets `stoppedAt`;
3. increments `droppedPointCount`;
4. stores `QUEUE_FULL` and a diagnostic message.

Native tracking then stops and emits a `QUEUE_FULL` callback error when a JavaScript bridge is available. Existing points remain readable and acknowledgeable. No old point is evicted silently.

A SQLite open/write/commit failure follows the same fail-closed path with state `failed` and code `PERSISTENCE_ERROR` where the database remains writable enough to record it. The original native error is logged without including coordinate values.

## Platform lifecycle

### Android

Persistent-track mode keeps the foreground service alive independently of the WebView, just as native URL mode currently does. The session ID and location configuration needed for a sticky restart are stored natively. A system-created `START_STICKY` service restores the active session and continues writing before any WebView exists.

Swipe from Recents is therefore expected to preserve an active persistent session. Android force-stop is an explicit operating-system stop and cannot be bypassed. On the next manual launch, the active session remains discoverable and can be resumed by calling `start()` with the same ID.

### iOS

The queue writes every `CLLocation` before bridge or HTTP delivery. Normal background execution and lock-screen delivery do not depend on JavaScript. The active session remains discoverable after ordinary application relaunch.

An explicit user force-quit normally prevents iOS from relaunching location tracking. The plugin preserves recoverable session metadata but does not promise to bypass this platform restriction. The host application must explain and resume the session after a later manual launch.

## Web behaviour

Persistent-track mode is native-only. The web implementation rejects `start({ persistentTrack: ... })` and all persistent queue methods with Capacitor's unimplemented error. It does not emulate durability with `localStorage` or IndexedDB because that would provide different lifecycle guarantees.

## Validation gates

Before the fork is tagged:

1. schema creation and migration tests pass on Android and iOS;
2. insert order, nullable fields, pagination, acknowledgement, reset, and session discovery have native tests;
3. overflow and injected write failure stop tracking without deleting earlier points;
4. stop/write races prove that every accepted point is either committed or produces an explicit failed session;
5. Android device tests cover background, lock screen, offline, swipe from Recents, process restart, reattach, stop, and reset;
6. iPhone tests cover background, lock screen, relaunch where permitted, stop, reset, and documented force-quit behaviour;
7. the example harness reads and acknowledges pages only after the native implementations are stable;
8. SGDMS integration acknowledges through a sequence only after its own SQLite transaction commits.
